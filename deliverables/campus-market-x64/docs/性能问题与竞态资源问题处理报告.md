# 校园二手交易平台：性能问题与竞态资源问题处理报告

报告日期：2026 年 9 月 1 日
系统版本：1.0.0
技术架构：React 19 + Spring Boot 3.3 + Spring Data JPA + MySQL 8.4 + Nginx

## 1. 报告目的与范围

本报告说明校园二手交易平台在商品浏览、收藏、下单、订单流转和后台审核场景中可能出现的性能瓶颈与并发竞态，并记录本次采用的治理措施、验证方法、已知边界和后续优化方向。分析范围覆盖前端静态资源、HTTP 反向代理、Spring Boot 服务、JPA 数据访问、MySQL 数据库以及上传资源持久化。

## 2. 系统关键链路

浏览器首先访问 Nginx 提供的 React 静态页面。`/api` 和 `/uploads` 请求由 Nginx 反向代理到 Spring Boot；后端通过 HikariCP 连接 MySQL。商品图片写入独立的 uploads 挂载目录，业务数据写入 MySQL 持久化目录。Docker Compose 仅暴露 8080 端口，数据库和后端位于内部网络。

关键一致性对象包括商品状态、订单状态、浏览次数、收藏次数、同一订单的评价记录及举报处理状态。其中商品状态与订单创建是一组跨请求竞争最明显的共享资源。

## 3. 性能问题分析与处理

### 3.1 列表无界返回导致内存与数据库压力

问题：商品搜索如果允许一次返回全部记录，会放大 SQL 扫描、对象映射、JSON 序列化与网络传输成本；页码或每页数量为异常值时还可能造成运行错误。

处理：商品搜索使用 Spring Data `Page`，页码下限归零，每页数量上限为 50，并允许按创建时间、价格和浏览量排序。浏览历史限制为最近 30 条。这样把单次请求的资源消耗控制在确定范围内。

### 3.2 高频筛选和关联查询缺少索引

问题：商品列表主要按状态、分类、卖家和创建时间过滤或排序；订单主要按买家、卖家、状态和创建时间查询。如果只依赖主键，数据量增大后会出现全表扫描和额外排序。

处理：为商品表增加 `(status, created_at)`、`(category_id, status)`、`(seller_id, created_at)` 组合索引；为订单表增加状态索引、买家/创建时间与卖家/创建时间组合索引，以及商品外键索引。收藏、浏览历史和评价通过唯一约束同时获得业务去重和索引能力。

边界：当前关键字搜索使用 `%keyword%` 模糊匹配，普通 B-Tree 索引无法高效命中。课程规模下可接受；数据达到十万级后应使用 MySQL FULLTEXT 或 Elasticsearch/OpenSearch，并通过压测决定迁移时点。

### 3.3 浏览量读改写产生锁竞争与丢失更新

问题：原实现为“先读 view_count，再在 Java 中加一并写回”。并发请求可能读取同一旧值，后提交的事务覆盖先提交结果，造成计数丢失。

处理：改为单条数据库原子更新：`update products set view_count = view_count + 1 where id = ?`。数据库在行级完成增量操作，不需要在应用内持有长事务，也避免丢失更新。更新后重新查询商品详情，保证响应展示的是数据库最新值。

### 3.4 静态资源和上传文件混入应用包

问题：若 React 静态文件由后端动态处理，或上传图片写入容器可写层，会增加 JVM 压力并在容器重建后丢失文件。

处理：React 构建产物由 Nginx 直接提供；上传资源挂载到宿主机 `resources/uploads`，后端仅负责上传校验与文件写入。Nginx 负责统一入口与反向代理，减少后端承担静态文件传输的开销。

### 3.5 仍需关注的 N+1 查询

商品 DTO 当前会查询卖家平均评分，并在登录状态下查询是否已收藏。列表映射时可能形成额外查询。课程数据量和每页 50 条上限下风险可控，但这是当前最明确的剩余性能优化点。后续可通过批量查询卖家评分和收藏关系、DTO 投影或专用列表查询一次性返回所需字段，并通过 SQL 统计验证查询次数。

## 4. 竞态资源问题分析与处理

### 4.1 同一商品被两个买家同时下单

竞态：两个请求都读取 `ON_SALE`，分别创建订单，可能出现“一件商品两笔有效订单”。

处理：创建订单前使用 `PESSIMISTIC_WRITE` 对商品行执行 `SELECT ... FOR UPDATE`。第一个事务获得锁后把商品改为 `RESERVED`；第二个事务只能等待，随后读到 `RESERVED` 并返回“商品当前不可交易”。商品编辑、卖家下架、重新上架和管理员下架也使用同一商品行锁，避免状态被旧数据覆盖。

### 4.2 订单状态被重复或越级推进

竞态：买家或卖家重复点击操作，或两个请求同时确认、付款、发货、收货，可能使状态校验基于同一个旧状态。

处理：订单动作先对订单行加写锁，再按固定状态机校验当前状态和操作者身份。只有 `待确认 → 待付款 → 待发货 → 待收货 → 已完成` 的合法转换能够提交；取消仅允许发生在待确认或待付款阶段。订单动作还锁定对应商品行，使“订单状态—商品状态”在同一事务内一致更新。

### 4.3 收藏计数丢失或重复收藏

竞态：同一用户重复收藏、不同用户同时收藏，可能造成重复记录或 `favorite_count` 丢失更新。

处理：收藏和取消收藏前锁定商品行，串行化计数修改；数据库对 `(user_id, product_id)` 设置唯一约束，作为最终幂等屏障。业务层先判断已收藏时直接返回，不重复增加计数。

### 4.4 重复评价与重复处理举报

竞态：同一用户并发提交两次评价，或两个管理员同时处理同一举报，可能生成重复评价或后处理覆盖先处理。

处理：评价前锁定订单行，并由 `(order_id, reviewer_id)` 唯一约束兜底。举报处理对举报行加写锁，只有 `PENDING` 状态允许处理；审核通过时还锁定商品行，并阻止对存在进行中订单的商品直接下架。

### 4.5 事务边界与锁顺序

涉及状态变化的方法均在事务中执行，校验、加锁、写订单和写商品属于同一提交单元。主要顺序为“订单行 → 商品行”或“举报行 → 商品行”；只操作商品的入口直接锁商品行。事务方法内不进行远程调用或大文件传输，减少持锁时间。若数据库检测到死锁，事务会回滚，不会留下半完成数据；生产环境可对幂等请求增加有限次数的退避重试。

## 5. 数据库约束与防御分层

并发正确性不只依赖 Java 判断，而采用三层防御：第一层是角色、所有权和状态机校验；第二层是事务与悲观写锁；第三层是数据库唯一约束和外键约束。订单号唯一、收藏唯一、浏览历史唯一、评价唯一，以及所有业务外键均由数据库保证。即使未来出现新的调用入口，数据库仍能拒绝破坏核心不变量的数据。

## 6. 验证结果

本次执行 Maven 集成测试共 5 项，结果为 5 通过、0 失败、0 错误。除登录鉴权、完整订单状态机、参数校验和图片上传外，新增两项并发回归测试：

1. 两个不同用户同时购买同一在售商品，断言最终只有一个 HTTP 200 成功响应。
2. 8 个线程并发发起 20 次商品详情访问，断言数据库浏览量精确增加 20，不出现丢失更新。

测试使用 H2 的 MySQL 兼容模式验证应用级事务和锁调用；最终交付环境使用 MySQL 8.4/InnoDB。镜像通过 Docker Compose 启动后还应执行登录、商品浏览、下单和上传图片的冒烟测试，并检查数据和资源在容器重建后仍然存在。

## 7. 监控与后续优化建议

1. 引入 Spring Boot Actuator 和 Micrometer，采集接口 P95/P99 延迟、错误率、JVM、连接池和慢 SQL 指标。
2. 打开 MySQL 慢查询日志，对 `EXPLAIN ANALYZE` 结果建立基线；数据量增长后再调整组合索引，避免无依据地堆叠索引。
3. 批量加载卖家评分与当前用户收藏关系，消除商品列表的 N+1 查询。
4. 图片进入对象存储并生成缩略图，使用 CDN 缓存；对上传内容增加更严格的文件签名校验。
5. 对订单创建接口增加客户端请求幂等键，减少网络重试带来的无效锁竞争。
6. 使用 Gatling、JMeter 或 k6 对商品列表、详情和下单分别压测，并以课程验收机器资源为基准记录吞吐量、P95 延迟和数据库锁等待。

## 8. 结论

本次处理将最重要的数据一致性风险集中到数据库事务和行锁中解决：同一商品不能生成两笔有效订单，订单状态不能并发越级，收藏和浏览计数不会因普通并发而丢失，重复评价和重复举报处理受到锁与唯一约束双重保护。性能方面已完成分页限流、热点索引、原子计数、静态资源分流和持久化挂载，并明确保留 N+1 查询与全文搜索作为下一阶段优化项。当前实现适合课程项目和中小规模校园使用场景。
